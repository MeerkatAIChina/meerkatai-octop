# 前端部分功能隐藏 — 技术规格

## 1. 目标

在权限层**之上**新增一层前端功能可见性开关，使 10 个目标入口对**包括管理员在内**的所有人不可见、不可达。仅改前端，可一处恢复。

## 2. 设计总则

- **集中声明，分散消费**：新增一个常量模块作为唯一事实来源，各渲染/判定点引用它
- **凌驾于权限层**：现有 `userCan()`（`permissions.ts:80-87`）对 `admin` 无条件放行，无法表达本次需求，因此判定必须独立于权限层
- **只断入口，不删代码**：页面组件、常量、路由定义一律保留
- **不引入构建期开关**：不做 env 覆盖、不加抽象层

## 3. 改动设计

### 3.1 集中开关（新增 `src/config/hiddenFeatures.ts`）

```ts
/** 对所有人隐藏的导航项 key。其路由树同时不可达。 */
export const HIDDEN_NAV_KEYS: ReadonlySet<string> = new Set([
  "bridge", "workbench", "remote-desktop", "acp",
]);

/** 对所有人隐藏的页内 tab key。key 全局唯一，故可共用一个集合。 */
export const HIDDEN_TAB_KEYS: ReadonlySet<string> = new Set([
  "oidc", "ldap", "updates",
]);

/** 左下角账户菜单中隐藏的项。 */
export const HIDDEN_ACCOUNT_MENU: ReadonlySet<string> = new Set([
  "helpFeedback", "projectUrl", "checkUpdates",
]);

/** 路径是否落在被隐藏的导航树内。 */
export function isHiddenRoute(pathname: string): boolean {
  for (const key of HIDDEN_NAV_KEYS) {
    if (pathname === `/${key}` || pathname.startsWith(`/${key}/`)) return true;
  }
  return false;
}
```

**设计说明**：4 个 nav key 加 `/` 前缀即为其路由前缀（`/bridge`、`/workbench`、`/remote-desktop`、`/acp`），因此**一份 `HIDDEN_NAV_KEYS` 同时驱动导航过滤与路由拦截**，不另维护路径表。

> 曾考虑让 `permissions.ts` 复用 `routes/index.tsx:137` 的 `resolveSelectedKey()` 做路径归并。已验证无循环依赖（`permissions.ts` 零 import，`routes` 不反向引用它），但会让被 22 个文件引用的底层工具反向依赖路由表，故不采用。

### 3.2 侧边栏过滤

`layouts/sidebarNav.tsx:134` `buildNavSections()` 返回前过滤：

- 剔除 `items` 中 key 命中 `HIDDEN_NAV_KEYS` 的项
- **剔除过滤后 `items` 为空的分组**

#### 为什么必须剔空分组

`控制` 分组（`:225-261`）恰好只含 `workbench` / `remote-desktop` / `acp` 三项，全部命中后该分组变成空壳。而 `sectionsFromLayout()`（`sidebarNavLayout.ts:195`）对空分组的处理**取决于用户有没有自定义过导航**：

| 条件 | 路径 | 空分组结果 |
|---|---|---|
| `layout === null`（从未自定义） | `:199` `if (!layout) return sections;` 提前返回 | **原样渲染** —— 残留一个空的「控制」标题 |
| 有已保存布局 | 经 `sectionForGroup()`（`:186` `items.length === 0 → null`） | 已被剔除 |

所以受害的是**从未自定义过导航**的用户（他们走 early return 那条路），必须在 `buildNavSections()` 里剔除。

#### 接口契约：一处过滤，两处生效

`Sidebar.tsx:397-400` 只构造一份 catalog，同时喂给两个消费者：

| 消费者 | 用途 |
|---|---|
| `sectionsFromLayout()` | 渲染侧边栏 |
| `<SidebarNavCustomizer catalog>` | 自定义导航的可选项 |

因此在 `buildNavSections()` 过滤一处即覆盖两者，**不需要单独改 `SidebarNavCustomizer.tsx`**。

#### 自定义导航面板的三层防线

该面板有三个区域（未分组 / 各自定义分组 / **已隐藏项**），逐层保证隐藏项不出现：

| 层 | 位置 | 作用 |
|---|---|---|
| 1 | `sidebarNav.tsx:134` catalog 过滤 | 4 项不在 catalog 中，「未分组 / 各分组」区天然没有 |
| 2 | `sidebarNavLayout.ts:104` `if (!catalogKeys.has(item.key)) continue;` | 历史布局引用过也不进编辑态；`:116-118` 补入「已隐藏项」的 key 取自**过滤后**的 catalog，故**「已隐藏项」区同样为空** |
| 3 | `SidebarNavCustomizer.tsx:321` `if (!item) return null;` | `ItemList` 按 key 回查 catalog，查不到即不渲染 |

第 1 层覆盖「没加过的人」，第 2、3 层覆盖「以前加过的人」。

#### 渲染侧兜底

`sectionsFromLayout()` 用 `catalogItems(sections)` 建查表后逐 key 回查（`:200-213`），查不到即 `filter(Boolean)` 丢弃。因此**绕过 UI 直接 PATCH `sidebar_nav` 塞入隐藏 key 也无效**——后端白名单未改，请求会成功落库，但前端渲染层不认。这是「仅改前端」这一边界仍然安全的原因。

### 3.3 路由拦截

改 `utils/permissions.ts` **两处**：

```ts
// routeNeedsPermission() 内，probe 计算之后
if (isHiddenRoute(probe)) return true;

// canAccessPath() 内，pathPermissionKeys 判定之前
if (isHiddenRoute(pathname)) return false;
```

**为什么必须两处**：`MainLayout/index.tsx:161-162` 仅在 `routeNeedsPermission(rc.path)` 为真时才包 `<RequirePermission>`。而 `/bridge` 的 `pathPermissionKeys()` 显式返回 `null`（`permissions.ts:185-187`，该页设计为「always available」），因此 `routeNeedsPermission("/bridge")` 为 **false**——`/bridge` 当前**没有任何权限包装**。只改 `canAccessPath()` 会漏掉它。

其余三条（`/workbench`、`/remote-desktop`、`/acp`）本就有包装，由第二条生效。

**响应契约**：`canAccessPath()` 返回 false → `RequirePermission.tsx:35` 渲染既有的 `ForbiddenPage`。**复用现有行为，不新增组件、不新增代码路径**。

### 3.4 页内 tab 过滤

过滤放在**声明 tab 的页面**（数据源头），而**不是**共用的 `hooks/useGatedSearchTabs.ts`。

理由：该 hook 是通用组件，职责只有「按权限筛选」与「管理 `?tab=` 查询参数」，它不掌握任何业务数据，也不知道 `oidc` / `ldap` 存在。把业务 key 塞进通用 hook，会让通用组件反向依赖业务配置。

两个页面各自把 tab 清单拆成 `ALL_TABS`（带类型标注）与过滤后的导出 `TABS`：

| 页面 | 命中 |
|---|---|
| `pages/Admin/Users/index.tsx` | `oidc` / `ldap` |
| `pages/Settings/AdvancedSettings/index.tsx` | `updates` |

```ts
const ALL_TABS: TabBarItem<TabKey>[] = [ /* … */ ];
export const TABS = ALL_TABS.filter((tab) => !HIDDEN_TAB_KEYS.has(tab.key));
```

**为什么要拆成两个常量**：`const x: T[] = [...].filter(...)` 不会把类型标注透传给数组字面量，直接写会被推断成 `{ key: string }[]` 而报 `TS2322`。

**`TabKey` 保持含 `oidc` / `ldap` / `updates`**，因此 `parseTab()` 与既有 `activeTab === "oidc"` 等渲染分支仍然类型合法（若从类型中删掉这些 key，会产生 `TS2367` 无重叠比较错误）。

**接口契约**：tab key 必须全局唯一，否则会误伤同名 tab。已核对三个相关页面的 key 集合——`local/roles/feishu/wecom/dingtalk/oidc/ldap`、`env-vars/observability/backup/https/updates/captcha`、security 页的 `hitl/filesystem/pii/tool_guard/skill_scan/audit`——无冲突。

**连带行为**：`allowedTabs` 减少后，该 hook 既有的「未知/缺失 tab 重定向到首个允许 tab」逻辑（`useGatedSearchTabs.ts:39-59`）自动生效；用户显式访问 `?tab=oidc` 会被判 `forbidden` 并渲染 `ForbiddenPage`，与整体一致。

### 3.6 纠缠重定向

共 9 条**注释掉**（保留代码，不删除），注释处标注隐藏项名称与恢复方法。其中 8 条在 `routes/index.tsx`，另 1 条是应用设置页内的 legacy 查询参数重定向：

| `routes/index.tsx` | `:243-245` | `/admin/updates` → `/admin/advanced?tab=updates` |
| `routes/index.tsx` | `:276-278` | `/updates` → `/admin/advanced?tab=updates` |

| `routes/index.tsx` | `:180-183` | `/terminal` → `/workbench/terminal` |

**另有两处非路由的入口，经确认不纳入本次范围**：`components/RemoteDisconnectBanner.tsx:35` 与 `pages/Chat/components/AgentNotReadyScreen.tsx:115` 的「打开云端协同 / 重连」按钮。

二者均以 `bridge_disconnected` 为渲染前提（`layouts/PageShell.tsx:216`、`pages/Chat/components/AgentNotReadyScreen.tsx:69`），而对端专家仅当存在 `status === "connected"` 的 bridge 连接时才会被载入（`context/AgentContext.tsx:254-257`）。本部署不存在任何 bridge 连接，且创建入口（`/bridge` 页，含 `bridgeApi.create()`）已随本需求关闭，故这两个按钮不会渲染。

## 4. 不改动的部分

| 对象 | 原因 |
|---|---|
| `SIDEBAR_NAV_KEYS`（`sidebarNav.tsx:51-71`）、`SIDEBAR_GROUPED_NAV_KEYS`（`:109-126`） | 需与后端 `octop.infra.users.preferences` 同步；隐藏只作用于渲染过滤，不动契约 |

| 后端与 `src/octop/` | 本次仅前端 |

## 6. 验收标准

1. **管理员**登录后，侧边栏无「云端协同 / 工作台 / 远程桌面 / ACP」，且「控制」分组整体消失
2. 直接访问 `/bridge`、`/workbench`、`/remote-desktop`、`/acp`（含子路径）均得 `ForbiddenPage`，管理员同样如此
3. 用户管理页无「通用 OIDC / LDAP」tab；应用设置页无「应用更新」tab
4. 账户菜单无「帮助与反馈 / 项目地址 / 检查更新」
5. 自定义导航面板的**三个区域**（未分组 / 各自定义分组 / 已隐藏项）均不含上述 4 个 nav 项；已保存过含这些项的布局时同样如此
6. 曾保存过含这些项的导航布局的用户，其布局数据不被破坏（隐藏项落入暂存）
7. 注释掉的 8 条重定向路径全部落到 `NotFoundPage`
8. `tsc -b`、`eslint`、`prettier`、上述测试全绿
