# 前端部分功能隐藏 — 需求调研

> 调研对象：`dashboard/` 的功能可见性与路由守卫。所有结论标注文件与行号。

## 1. 已澄清的需求边界

| 维度 | 决定 |
|---|---|
| 隐藏程度 | **页面不可达**，不只是藏入口 |
| 适用对象 | **含管理员在内，所有人不可见** |
| 实现形态 | **集中开关**：一处声明，多处消费 |
| 改动范围 | **仅前端**；后端 API 与权限模型不动 |
| 指向被藏页面的旧路径 | **注释掉**（保留代码，不删除） |
| 自定义导航 | 可选项里过滤掉那 4 个 nav 项 |

## 3. 现有可见性机制，以及它为什么不够用

两条现成链路：

| 链路 | 入口 | 声明表 |
|---|---|---|
| 侧边栏 | `sidebarNav.tsx:134` `buildNavSections()` → `navAllowed()` | `permissions.ts:32-47` `NAV_PERMISSIONS` |
| 页内 tab | `hooks/useGatedSearchTabs.ts:28-34` | `permissions.ts:51-59,61-68,70-77` |

两条链路最终都汇到同一个判定：

```
permissions.ts:80-87
  if (user.role === "admin") return true;   ← 管理员无条件放行
```

**管理员绕过所有权限门。** 所以「把 `oidc`/`ldap` 从权限集里摘掉」这类做法对管理员无效，无法满足第 1 节的需求边界。隐藏必须做在权限层**之上**，而不是复用权限层。

## 4. 路由守卫链路

```
routes/index.tsx:146-290          路由表
  ↓
MainLayout/index.tsx:161-162      if (routeNeedsPermission(rc.path)) el = <RequirePermission>{el}</RequirePermission>
  ↓
permissions.ts:223-232            routeNeedsPermission()   决定哪些路由要包
permissions.ts:234-241            canAccessPath()          实际校验，不过则渲染 ForbiddenPage
```

**接入点唯一**：只需在 `canAccessPath()` 里增加「被藏路径一律拒绝」的判断，即可凌驾于 `admin` 之上，无需改几十条路由定义。

## 5. 侧边栏与自定义导航同源

`Sidebar.tsx:397-400` 只构造一份 catalog，同时喂给两个消费者：

```
buildNavSections(user, { mobileEnabled })
   ├─→ sectionsFromLayout()            渲染侧边栏   Sidebar.tsx:403-406
   └─→ <SidebarNavCustomizer catalog>  编辑器的可选项  Sidebar.tsx:537-543
```

因此在 `buildNavSections()` 里过滤一处，即可同时覆盖「导航栏入口」和「自定义导航可选项」，不需要单独改 `SidebarNavCustomizer.tsx`。

**副作用是良性的**：`sidebarNavLayout.ts:143-152` `preservedPlacements()` 把「在 catalog 中不存在、但存在于用户已保存布局里」的 key 归入暂存。

```ts
const visible = new Set(catalogItems(sections).keys());
return layout.items.filter(item => NAV_KEY_SET.has(item.key) && !visible.has(item.key));
```

隐藏项因此落入暂存而非被丢弃，用户已保存的导航布局不被破坏——正符合「暂时隐藏、将来放开」的定位。

## 6. 重定向纠缠

处理方式：注释掉，保留代码便于将来恢复。

## 7. 不可动的契约

`sidebarNav.tsx:50` 明确要求 `SIDEBAR_NAV_KEYS`（`:51-71`）与后端 `octop.infra.users.preferences` 保持同步；`SIDEBAR_GROUPED_NAV_KEYS`（`:109-126`）同理，且被 `sidebarNavLayout.ts:43` 的 `NAV_KEY_SET` 使用。

**这两份常量全部保持原样**，隐藏只作用于渲染过滤。后端契约因此不受影响，满足「仅前端」的边界。

## 9. 结论

需求可满足，且改动收敛：

- 在权限层之上新增**一层集中开关**；判定优先级高于 `userCan()` 的 admin 放行
- 消费点共 **5 处**：`buildNavSections()`（覆盖导航栏 + 自定义导航）、`canAccessPath()`、用户管理页 `TABS`、应用设置页 `TABS`、`AvatarDropdown.tsx`
- 另加 9 条纠缠重定向的注释（8 条在 `routes/index.tsx`，1 条是应用设置页的 `?tab=bridge`）
- `SIDEBAR_NAV_KEYS` / `SIDEBAR_GROUPED_NAV_KEYS` 与后端权限模型**均不改动**，不触及 `src/octop/` 内核
