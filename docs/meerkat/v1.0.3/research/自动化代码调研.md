## 1. 结论

可以在 Octop 内新增原生自动化模块，专家、Skill、运行接口、工作空间、登录及持久化基础可以复用。需要新建持久化运行账本、调度器、输入发现、产出管理及页面。现有定时触发或执行结束事件，不能单独承担可靠的业务运行管理。

## 3. 工作空间与存量边界

沿用仓库的 `HarnessAgent.workspace` / `BackendWorkspace` 约定；内容读写不能绕过它直接操作专家目录。HTTP 路径规范化与工作空间内路径语义分开，不能把 BackendWorkspace 的 `/` 和 `.` 混为一谈。

输入输出首先绑定现有专家工作空间。这是范围取舍，不能理解为已经支持用户电脑上的任意目录。工作空间在服务端，浏览器本地目录只通过上传进入；目录选择页必须说明这一点。

取消信号、租约失效、WebSocket 结束和进程重启都不能证明工具已停止，也不能证明产出合格。未知状态必须先核对，外部副作用无法判定时等待人工，不自动重新调用。

## 4. 开发前验证门槛

1. 用两个普通专家验证专属线程的 stream、取消、历史和用量记录。
2. 用需人工确认的 Skill 验证等待、服务重启、恢复及重复确认；不能只测连续在线场景。
3. 验证选定 BackendWorkspace 版本的二进制读写、目录分页、远程存储和打包；缺失能力先补通用工作空间接口，不在自动化里判断 backend 类型。
4. 确认目标数据库已应用版本及版本发布情况，再决定迁移编号；不直接改已应用的 020 来期待新表自动出现。
