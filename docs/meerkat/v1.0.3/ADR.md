# 自动化架构决策记录

状态：待评审，2026-10-11。以本轮用户明确选择的原生产品方向为依据。

## ADR-01 原生自动化模块

- 背景：用户要求增加产品能力，统一菜单、身份、专家、存储和部署。
- 决策：新增 infra/automation、原生 API/页面和同库账本，由 OctopServer 管理生命周期。
- 未选方案：外置调度服务、浏览器控制多个窗口、独立工作台；这些会分裂部署、权限与运行记录。
- 后果：需要小范围核心接线（server、services、config、路由），必须专项回归启停和备份重绑定。领域逻辑留在新模块，不重构存量内核。

## ADR-02 复用专家与 Skill，平台保持通用

- 背景：用户以后会创建其他业务专家，不能只服务专利分析。
- 决策：首版每计划选择一个已有普通专家；平台只管理触发、运行、尝试、事件与产出。
- 未选方案：专利专用页面/状态/表、另一套专家库、自动克隆专家、团队嵌套编排。
- 后果：专业质量由 Skill 和业务校验协议定义；首版不能保证任意专业结论正确。配置变化需要指纹核对，不伪称完整专家版本隔离。

## ADR-03 首版输入输出绑定专家工作空间

- 背景：用户需要配置文件来源和交付目录；现有工作空间已有本地及远程存储抽象。
- 决策：上传及目录通过 BackendWorkspace 完成，首版一文件一 Run；专属快照和尝试目录。
- 未选方案：任意宿主机路径直接读写、另建文件存储层、一次加入所有云盘连接器。
- 后果：不能直接选浏览器本地目录持续监听；后续可新增通用输入源适配器，仍复用相同 Run/Artifact 模型。

## ADR-04 持久化运行账本与安全恢复

- 背景：流结束、内存队列与租约失效均不足以证明业务完成。
- 决策：Run/Attempt/Event 持久化；唯一键、条件更新和 lease token 去重；未知先 reconciling，有副作用未知等待人工。
- 未选方案：仅依赖 Cron/内存状态，重启后全部重跑，只凭 done 记成功。
- 后果：增加恢复实现与验收工作量；平台不承诺外部工具 exactly-once，也不自动批准人工请求。

## ADR-05 单进程、有限并发、不增加必需服务

- 背景：Octop 当前产品部署是一套原生服务，用户要求减少对存量影响。
- 决策：首版单活动服务进程，DB 协调行防误领；建议全局并发 2、每专家自动化并发 1，有界扫描与退避。
- 未选方案：Redis/Celery、独立 Worker 集群、第一版多机高可用。
- 后果：SQLite/PG 都支持，但不等于支持多实例分布式执行；实际资源影响需负载验证。

## ADR-06 新菜单兼容旧自定义布局

- 背景：现有布局转换会将未保存的新键视为隐藏，且用户要求保护旧功能。
- 决策：只补缺失 automation 项，默认跟随可见 tasks；显式隐藏优先，不覆盖已保存布局。
- 未选方案：重置用户导航、让旧用户自己发现并开启菜单、泛化为所有新项自动显示。
- 后果：需要前后端导航键同步和布局专项测试，不恢复既有隐藏功能。

## ADR-07 增量迁移与保留数据回退

- 背景：现有 DB 已有 schema watermark，修改已应用迁移会漏新增表。
- 决策：开工核对已应用/已发布版本，遵守成对迁移规则；回退先停用功能并保留新表，程序 schema 兼容性单独验证。
- 未选方案：无条件折入 020、发布失败后删除新表、直接覆盖活动 DB。
- 后果：迁移、旧程序兼容与备份恢复是发布门槛；不能把新页面可用当成原生集成已完成。
